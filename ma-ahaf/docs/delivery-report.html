MA-AHAF — Multi-Agent Adaptive Hallucination Attenuation Framework

A model-agnostic adaptive layer between an application and its LLMs that decides, per request, how factual, how grounded, how verified, and how creative the answer should be — with a full audit trail. This report documents what was built against project proposal final.pdf, the technology, the request workflow, a file-by-file map of the codebase, and the measured evaluation.

1Executive summary

Conventional hallucination mitigation trades one goal for another: heavy grounding kills useful creativity; free generation invents facts. MA-AHAF treats reliability and creativity as a per-request operating point, not a fixed mode. For every request a closed-loop controller estimates hallucination risk, evidence coverage, source agreement, claim criticality, ambiguity and creativity demand, and from those picks a six-parameter policy that governs how much grounding, verification, citation, uncertainty disclosure, revision and abstention are applied.

What was delivered in this engagement:

  • All 13 agents from proposal §7, an ARCOP adaptive controller (§8), the claim-level H(x) risk model (§9), a Claim Risk Graph, evidence triangulation (§11) and a model-agnostic LLM gateway (§12).
  • A FastAPI service (API-key + JWT + RBAC, tenant isolation, PII redaction, OpenTelemetry + Prometheus, OpenAPI docs) and a React dashboard with a live Playground, trace explorer, human-review queue, metrics and evaluation views.
  • A 143-document knowledge base across 13 domains, a 77-item labelled benchmark, an automated evaluation harness (MA-AHAF vs static-RAG baseline), and a retraining loop that refits the risk model and calibrator from real eval labels.
  • Deployment artifacts: docker compose stack, Kubernetes manifests, a k6 load-test, a security review, and five documentation files.
Headline evaluation result (77 items, gpt-4o-mini). Confidence calibration error ECE 0.191 → 0.066 (−65%), and MA-AHAF abstains on 15.8% of items — every one on the deliberately un-answerable high-stakes set, where the static-RAG baseline always answers. The framework's core §5/§10 objectives — calibrated confidence and safe abstention — hold. The price is latency and cost (~9–14×), which the policy spends only where risk warrants.

3Architecture & workflow

MA-AHAF is an adaptive orchestration layer. The application calls POST /v1/generate; the layer returns a controlled response plus evidence, per-claim risk, calibrated confidence, the policy vector, an action (answer / qualify / abstain / escalate) and a full agent trace.

The canonical flow is a LangGraph state machine (app/orchestration/graph.py, exposed as Mermaid at GET /v1/graph). The runtime executes the same nodes through an explicit, debuggable bounded loop (app/orchestration/pipeline.py) so state merging is never ambiguous. A single pydantic RequestState object is threaded through every step.

4Request lifecycle

What actually happens when a prompt arrives, in order:

  1. Redaction & state. PII (email, phone, SSN, card, IP) is stripped (core/security.py) before the prompt is stored or sent anywhere. A RequestState and a per-request UsageMeter are created.
  2. Intent + risk. Zero-shot classification assigns a task type and ambiguity; the risk profiler scores consequence, domain risk (medical / legal / financial / safety keyword hits), numeric load and a task prior into a single request risk.
  3. Policy. ARCOP turns those signals into a six-parameter policy vector — grounding intensity, verification depth, creativity allowance, citation requirement, abstention threshold, escalation threshold — plus a candidate count. Tenant profile and bounded caller overrides apply.
  4. Grounding-first retrieval (only if grounding intensity is high): fetch prompt-level context so the draft is grounded from the start rather than generate-then-check.
  5. Generation. The gateway's generator model produces N candidates; temperature scales with creativity allowance. The most-cited / longest candidate becomes the working draft.
  6. Decomposition. An LLM extracts atomic, independently checkable claims; each is typed (factual / numeric / causal / temporal / opinion / creative), scored for criticality and temporal sensitivity, and linked into a Claim Risk Graph by shared entities.
  7. Evidence + source quality. Per non-creative claim: optional query expansion, then hybrid retrieval (vector + BM25 → reciprocal-rank fusion → MMR → cross-encoder rerank), including a search for contradictory evidence on risky claims. Each passage is scored for authority, freshness, relevance, consistency and corroboration.
  8. Verification. NLI (local DeBERTa-v3, or the gateway verifier model as a batched entailment judge) tests claim ⊨ evidence. Standard-and-deeper verification adds an independent LLM verifier; deep verification adds a counterfactual probe (“what evidence would falsify this?”) for critical claims. The contradiction agent scans for conflicting evidence and internal inconsistency between claims.
  9. Risk scoring. The claim-level H(x) model produces a calibrated risk per claim with a per-feature explanation; risk propagates along the graph's dependency edges (bounded, never amplifying).
  10. Creativity. distinct-n, inter-candidate self-BLEU diversity and embedding novelty vs the evidence centroid; explicitly creative spans are located and protected.
  11. Revision loop (bounded by MAAHAF_MAX_REVISION_LOOPS): if critical claims are unsupported or high-risk, the reviser rewrites or hedges them while a creativity-preservation gate shields <keep> spans, then the draft is re-decomposed and re-verified.
  12. Decision. The abstention agent combines calibrated confidence, the hallucination budget (near-zero for high-stakes), critical-unsupported count, agent disagreement and the policy thresholds into one action, and segments the answer into factual / assumption / creative parts.
  13. Finalize + audit. The user-facing response is assembled (with an uncertainty banner for qualify, a withhold message for abstain). The audit agent records the full trace, agent votes and pinned model versions; escalations and high-stakes abstentions enter the human-review queue.

6ARCOP & the hallucination risk model

Adaptive Reliability–Creativity Operating Point (proposal §8)

app/controller/arcop.py computes a policy vector per request rather than selecting a static mode:

π = f(Risk, Intent, EvidenceCoverage, ClaimCriticality, Ambiguity, SourceAgreement, CreativityDemand, ModelConfidence, Cost, Latency)

exposing grounding intensity, verification depth (light / standard / deep), creativity allowance, citation requirement, abstention threshold and escalation threshold. The default is an interpretable rule / scoring engine; a trained policy.joblib (MultiOutput GradientBoosting) can be blended 50/50 and is then re-clamped to the rule engine's safety floor so a poor learned policy can never switch off verification, citation or abstention on a risky request. Tenant profiles (strict / balanced / creative) and caller overrides (bounded to ≤ 0.3 loosening) adjust the vector.

Claim-level hallucination risk H(x) (proposal §9)

H(x) = w₁(1−EvidenceCoverage) + w₂·Contradiction + w₃·SourceRisk + w₄·ModelUncertainty + w₅·ClaimCriticality + w₆·TemporalSensitivity + w₇·AgentDisagreement

Implemented in app/controller/risk_model.py as a calibrated logistic model whose coefficients are the learned w₁..w₇, with the proposal's hand-set weights as a fallback. Every score returns normalised per-feature risk_contributions — an explanation of why a claim is high risk — and risk then propagates along the Claim Risk Graph's dependency edges. A separate hallucination budget (controller/budget.py) sets a context-specific tolerance for unsupported claims: ~0.05 for high-stakes, ~0.85 for creative.

11Evaluation & results

Methodology

Systems. MA-AHAF (the full 13-agent pipeline) vs a static-RAG baseline — the same generator model and the same hybrid retriever, top-5 passages in context, but no adaptive control, verification, revision or abstention. Both use the identical retrieval stack and generator, so the delta isolates the adaptive attenuation layer.

Benchmark. 77 labelled prompts over a 13-document corpus, across five task types (factual 31, high-stakes 17, analytical 12, creative 10, mixed 7). 8 high-stakes items are deliberately un-answerable from the corpus, to test calibrated abstention. Run on gpt-4o-mini for generation, decomposition, verification and revision, with local bge-small + BM25 + cross-encoder retrieval; 76 / 77 items completed (one timed out during a transient network drop).

Interpretation

Genuine wins. Confidence calibration improves markedly and MA-AHAF abstains only where it cannot ground the answer — the proposal's core §5 / §10 objectives. Unsupported-claim rate is flat because with gpt-4o-mini as the generator the raw answers are already fairly grounded on this benchmark, so there is little headroom — the value there is the abstention on the cases it cannot ground, not a lower rate on the cases it answers.

Two apparent regressions are metric artifacts, not real. Citation precision (0.82→0.15 in the raw run): the two systems are not scored the same way — the baseline number is answer-level entailment, the MA-AHAF number is true claim-level precision over every decomposed atomic claim. Scored symmetrically, citation recall is 0.82→0.83. Creativity (0.99→0.65 in the raw run): the baseline generates one candidate, so its self-BLEU is 0 and its diversity term is a free 1.0; MA-AHAF pays real inter-candidate self-BLEU. On the creative split MA-AHAF scores 0.808 — creative quality is retained. The full docs/final-report.md §4.2 carries the detail.

Retraining loop

retrain_from_eval.py refit the risk model (213 claim rows, held-out AUC 0.751; dominant predictors of an unsupported claim: agent disagreement and source risk) and the calibrator (ECE 0.106 → ~0). The retrained artifacts are archived, not shipped as the runtime default — 213 rows on a 13-document benchmark is far too little to trust (the fit collapsed the missing-evidence weight to zero). This pass proves the loop is wired end-to-end; a production run needs the ≥ 500-prompt client benchmark from §5.

14Limitations & next steps

  • Benchmark scale. 77 synthetic items on a 13-document corpus — directional, not representative of a production domain. A real engagement needs a client corpus and ≥ 500 human-labelled prompts.
  • Same judge family. On the OpenAI path the generator and the entailment judge are both gpt-4o-mini. Point MAAHAF_LLM__VERIFIER_MODEL at a different family, or set MAAHAF_NLI_BACKEND=local, before quoting headline numbers. The production k8s ConfigMap already sets local.
  • Eval metric symmetry. Citation-precision and creativity are scored differently for the two systems (see §11). Making them symmetric is a small, worthwhile fix.
  • Production stack unverified on a host. Docker / Kubernetes were not exercised on a live cluster in this engagement (no Docker on the build machine); the manifests are a reference.
  • Learned ARCOP policy. Still trained on synthetic data; only the risk model and calibrator are refit from real eval labels in this pass.
  • Roadmap (§20): learning-to-route controller from production feedback, personalised policies, multimodal verification, live web-freshness monitoring, domain-expert agents.
